# 엑셀 기반 통합 여행 운영 웹앱 개발 계획

작성 기준: 2026-11-13. 이 문서는 구현 전 설계안이다. 근거는 docs/01~05, seed-data/ex.md, seed-data/dw.md, 두 원본 엑셀과 현재 웹앱 소스의 읽기 전용 분석이다. 앱 코드는 수정하지 않았다.

## 1. 목표와 경계

하나의 웹앱 안에 필리핀, 태국, 일본의 예약 관리 공간을 각각 둔다. 탐색, 목록, 상세, 저장 방식은 통일한다. 각 공간은 자기 나라의 예약 목록, 입력 항목, 업무 규칙, 집계 범위를 가진다. 국가별 상품, 수배, 요금, 정산, 취소 규칙은 독립적으로 적용한다. 데스크톱에서는 엑셀처럼 한눈에 많은 예약을 볼 수 있고, 모바일에서는 같은 내용을 카드와 날짜별 상세로 확인한다.

엑셀을 그대로 옮긴다는 것은 각 시트의 값, 수식 원문, 메모, 배경색, 숨김 행, 병합 범위, 조건부 서식과 예약 간 관계를 잃지 않는다는 뜻이다. 운영 화면은 검색과 수정에 적합하게 재구성한다. 원본 셀은 별도 원본 보기에서 좌표와 함께 확인한다.

신규 예약에는 현재 코드의 추천 형식을 사용하고 수기 입력도 허용한다. 이관된 코드 계열의 의미·약호, 색상 범례, 국가별 정산·취소 규칙은 사용자가 나중에 제공한다. 태국 전용 엑셀과 규칙도 아직 없다. 미확정 뜻을 추측해 자동 계산하거나 상태를 바꾸지 않는다.

## 2. 기존 문서와의 관계

| 기존 문서 | 재사용할 개념 | 새 설계에서 고칠 점 |

| 02 기능 명세서 | 예약 목록/상세, 일정, 바우처, 낙관적 동시성 | 일반 화면은 즉시 접속. 삭제 등 관리자 동작에서만 비밀번호 모달. 신규 코드 추천과 수기 입력을 함께 제공하고 상태 자동 전이는 보류. |

## 3. 최소 기능 범위

### 먼저 필요한 기능

1. 로그인 없이 필리핀 예약 화면에 바로 접속. 예약 삭제·원본 이관·관리 설정 변경에서만 관리자 비밀번호 모달과 세션 확인.
2. 국가별 예약 관리 공간: 필리핀, 태국, 일본. 첫 진입의 기본 국가는 필리핀이다. 각 공간의 예약 목록·입력 화면·검색 조건을 독립적으로 제공한다. 전체는 교차 검색·조회용이며 통화별 합계를 유지한다.
3. 국가별 예약 목록: 날짜·상태·거래처·코드·손님 검색, 빠른 상세 진입. 데스크톱 메인은 2025 MAR 원장의 열·월 구획·배경색·메모가 익숙한 엑셀형 표로 표시한다. 행 hover는 반대색으로 강조하고 행 클릭은 상세 편집을 연다. 각 행 **맨 오른쪽 마지막 열**의 정산서 버튼은 해당 예약 정산 모달을 연다. 다른 국가의 예약이 기본 목록에 섞이지 않게 한다.
4. 예약 상세: 기본 정보, 날짜별 호텔/골프/차량/투어, 확인번호, 메모, 결제·비용, 취소·변경 이력. 각 값의 원본 위치 확인.
5. 필리핀 시제 장부와 클락 거래처별 협력업체 바우처 폴더, 일본 수배 명단·호텔·골프·차량 정보 조회 및 필요한 필드 수정.
6. 엑셀 가져오기 미리보기와 검토 목록: 모호한 코드·날짜·금액·색의 뜻을 확정하기 전에도 원본 전체를 조회.
7. 모바일에서 예약 검색·조회, 일정·바우처 번호 확인, 필요한 상태·메모 수정.
8. DW Tour의 독립 정산서 메뉴: 국가·기간별 전체 정산 표와 예약별 상세 모달. 필리핀 원장의 AD:AQ 원본 열을 보존하고 AP/AQ의 미확정 뜻은 임의 계산하지 않는다.
9. DW Tour 공통 헤더 환율: 네이버 원화 기준 USD 1·PHP 1·JPY 100 값과 고시 시각을 표시한다. 매일 06:00 한국시간 서버 확인과 일반 화면 새로고침을 제공한다.
10. 신규 예약 코드는 현재 시스템 형식으로 자동 추천하거나 수기로 입력한다. 엑셀 이관 코드는 원문 그대로 유지한다.

### 뒤로 미룰 기능

색상만으로 상태 확정, 가이드 수익 자동 배분, 자동 마감·자동 이월, 복잡한 통계 화면, 전면 오프라인 편집, 새 계정 등록과 세부 권한 관리. 신규 예약의 기존 시스템 코드 추천과 수기 입력은 첫 범위에 포함한다. 기존 문서에 적힌 상태 자동 전이는 새 설계의 확정 규칙이 아니다.

상단에는 국가 선택과 검색을 두고, 메뉴는 모바일에서 열 수 있는 버튼/하단 탐색 중 한 방식으로 제공한다. 화면 폭 360px부터 주요 기능이 동작해야 한다. 터치로 열 수 없는 hover 전용 메모는 만들지 않는다. 엑셀 색은 원본 표시용이고, 웹앱의 상태 배지는 국가에 관계없이 같은 뜻을 갖는다. 색이나 아이콘만으로 상태를 전달하지 않고 텍스트를 함께 쓴다.

### 국가별 예약 관리

| 공간 | 첫 화면과 예약 상세 | 규칙 적용 범위 |
|---|---|---|
| 필리핀 예약 | 필리핀 예약 달력·목록, 호텔/골프/차량, 시제와 바우처 연결 | 필리핀 원본과 확정된 필리핀 규칙만 적용 |
| 태국 예약 | 별도 예약 달력·목록과 입력 틀을 제공하되, 아직 없는 원본·규칙은 빈 상태와 미확정 항목으로 표시 | 태국 전용 원본과 규칙을 받은 뒤 확정 |
| 일본 예약 | 일본 수배 명단 중심 목록·상세, 호텔 객실/박수, 골프 티오프, 차량·기사와 비용 | 일본 원본과 확정된 일본 규칙만 적용 |

첫 진입 시 필리핀 예약 화면을 열고, 현지 날짜가 속한 달을 기준으로 이전 달·현재 달·다음 달을 한 화면에 표시한다. 예를 들어 오늘이 2026-11-13이면 2026년 10월 1일부터 12월 31일까지다. 월 이동 시 이 3개월 창을 한 달씩 옮긴다. 다른 국가를 처음 열 때도 같은 기본 기간을 사용한다. 이후에는 세 공간이 각각 마지막으로 본 기간·필터를 유지한다. 예약을 만들 때 소속 국가는 필수이고, 그 나라의 입력 항목과 마스터만 기본으로 보여준다. 전체 검색 결과에서 예약을 열면 해당 국가의 상세로 이동한다. 국가를 바꾸어도 예약의 소속과 통화가 저절로 바뀌지 않는다.

필리핀 안의 클락 업무에는 별도 협력업체 바우처 폴더를 둔다. KDS, Monkey(몽키), THE CLARK TOUR(더클락투어), CLARK GOGO(클락고고), GOLDEN RIVER(골든리버)는 클락의 주요 거래처별 탭이다. 골프장·호텔은 해당 예약 서비스를 제공하는 협력업체이므로 거래처와 별도 필드·검색 조건으로 둔다. 거래처 탭의 행은 수배와 바우처를 정리한 업무 행이며, 모두를 별도 신규 예약이나 바우처 발급 완료 건으로 보지 않는다. 예약 상세에서는 이 행과 연결된 바우처·결제·메모·원본색을 볼 수 있다.

## 5. 데이터 구조와 이관

### 원본 보존층

- import_batches: 파일, 해시, 업로드 시각, 파서 버전, 처리 결과.
- source_rows/source_cells: 시트명, 행번호, 셀 좌표, 값의 타입, 원문, 수식, 저장된 계산값, 메모 원문·작성자, 숨김 여부와 출처.
- source_styles 또는 압축된 색 구간: 직접 채우기 색의 RGB/테마/tint, 빈 셀의 색, 병합 범위, 조건부 서식 규칙. 원본 화면에 필요한 범위만 요청 시 읽는다.
- 원본은 불변으로 두고, 구조화 결과를 고치더라도 원본 셀과 원래 색을 다시 볼 수 있어야 한다.

### 운영층

- markets(PH/TH/JP), reservations(내부 UUID, 필수 시장 ID, 원본 코드, 대표자, 인원, 기간, 확인된 상태). 예약 하나는 주 운영 국가 하나에 속한다.
- reservation_sources: 같은 예약을 가리키는 여러 원본 행의 근거. 코드가 같다는 이유만으로 자동 병합하지 않는다.
- voucher_sheet_entries와 supplier_voucher_items: 클락의 거래처 탭 원본 행을 보존하고, 한 행의 여러 날짜별 골프장·호텔 수배/바우처 항목을 분리한다. 거래처, 공급처, 예약, 일정 연결은 각각 별도로 두고 모호하면 미확정 상태로 둔다.
- itinerary_items: 날짜별 골프, 호텔, 차량, 투어, 미팅·샌딩. 서비스마다 여러 시간과 확인번호를 연결.
- service_confirmations: 호텔 예약번호, 골프 바우처, 교통 번호를 종류별로 여러 개 저장.
- cost_lines와 payment_transactions: 단가/수량/추가금/실제 금액과 고객 입금/공급처 지급/환불을 구분. 통화는 각 거래에 붙인다.
- reservation_events: 취소, 날짜·시간·인원 변경, 복원 이력. 과거 값과 원본 메모를 유지.
- 일본 손님 명단, 호텔 객실·박수, 골프 티오프·추가 요금, 차량·기사 배정은 일정에 연결된 세부 항목으로 둔다. 필리핀 시제는 cash_transactions로 분리한다.

기존 bookings의 code UNIQUE와 vouchers.booking_code 문자열 연결은 엑셀의 중복 코드와 충돌한다. 신규 데이터는 내부 UUID로 연결하고, 기존 필드가 필요하면 전환 기간 동안 읽기 호환 계층을 둔다. 1TH~6TH, memo_1~6을 새 예약의 유일한 저장소로 사용하지 않는다. 태국은 시장 항목만 준비하고 근거 없는 파서와 요금 표를 생성하지 않는다.

국가별 예약 화면은 필수 시장 ID로 서버에서 범위를 제한한다. 지점(branch)은 국가 안의 지역·사무소 정보로 별도 보관한다. 공통 일정 모델을 쓰더라도 국가 전용 필드와 검증·정산 규칙은 시장별 모듈로 분리한다. 국가 간 동일 코드, 동일 손님 이름, 동일 호텔명만으로 예약을 합치지 않는다.

### 가져오기 순서

파일별 읽기 → 모든 셀·메모·색·숨김/병합/조건부 서식 보존 → 행 유형 분류 → 예약/일정/비용 후보 생성 → 국가 및 중복 후보 표시 → 관리자 검토 → 운영 데이터 확정. 원본 코드, 색, PAID/OK 등의 뜻을 모르면 미확정으로 남긴다.

두 원본 파일은 합계 10개 시트, 값/수식 셀 39,142개, 메모 3,436개다. 일본 수배의 숨김 행에도 값과 메모가 있다. 동일 코드가 여러 행에 있으며 두 파일 간 같은 일본 코드도 5개 확인됐다. 이 수치는 최초 이관 대조 기준이며 파일이 바뀌면 다시 계산한다.

클락의 거래처별 5개 시트에는 바우처·비용·지급 날짜로 보이는 정보가 값과 메모에 섞여 있다. KDS E3:F3 열 밀림, Monkey와 THE CLARK TOUR 앞부분의 복사 행, CLARK GOGO의 결제 문구, GOLDEN RIVER의 메모 안 복수 번호를 그대로 보존하고 검토한다. 색은 탭·행·셀별로 중요하지만, 녹색·노랑·빨강을 지급/확정/취소 상태로 자동 확정하지 않는다.

## 6. 관리자 비밀번호와 데이터 접근

첫 접속에서 로그인 화면을 보여주지 않는다. 일반 예약 조회·추가·수정은 바로 사용한다. 예약 삭제·원본 이관/검토 확정·관리 설정 변경에서만 관리자 비밀번호 모달을 띄운다. 새 Supabase 프로젝트에 한 개의 고정 관리자 계정을 사전에 만들고 비밀번호를 Auth로 검증한다. 여러 사람이 비로그인 상태에서 수정하면 개인별 작성자를 식별할 수 없으므로 시각·변경 전후 값과 요청 근거를 이력으로 남긴다.

최소 보안 조건은 다음과 같다.

1. 공개 회원가입은 끄되 미로그인 일반 조회·예약 추가·수정은 허용한다. 삭제·이관·관리 설정 변경은 지정 관리자 세션이 없으면 서버에서 거부한다. 비밀번호 시도와 비로그인 쓰기 요청 모두 호출량을 제한한다.
2. 브라우저에 관리자 비밀번호, 데이터베이스 비밀키, service_role 키를 넣지 않는다. HTTPS와 정상 세션 만료·로그아웃을 사용한다.
3. Supabase Data API에 노출되는 테이블·뷰·함수는 일반 사용자의 조회/추가/수정 가능 범위와 관리자 전용 삭제·설정 변경 범위를 각각 검사한다. 프론트의 버튼 숨김만으로 삭제를 보호하지 않는다.
4. 기존 보고서 뷰도 원본 테이블의 접근 제한을 우회하지 않는지 검토한다. 민감한 손님 명단·메모를 공개 뷰와 공개 캐시에 넣지 않는다.
5. 로그아웃 시 기기에 남은 예약 캐시를 지운다. 모바일 공용 기기에서 이전 손님 정보가 보이지 않아야 한다.

이 방식은 일반 화면을 바로 열고 필요한 순간에만 비밀번호 한 칸을 제공한다. Supabase는 [공개 테이블에 대한 접근 권한과 RLS](https://supabase.com/docs/guides/api/securing-your-api), [회원가입 비활성화](https://supabase.com/docs/guides/auth/general-configuration), [인증 요청 제한](https://supabase.com/docs/guides/auth/rate-limits), [뷰의 RLS 적용](https://supabase.com/docs/guides/database/postgres/row-level-security)을 별도 설정으로 설명한다. 구현 시 현재 프로젝트 설정을 확인한다.

## 7. 느린 인터넷에서의 속도 기준

| 지점 | 설계 기준 |
|---|---|
| 첫 목록 | 필리핀을 기본으로 열고, 현지 오늘이 속한 달의 이전 달·현재 달·다음 달, 총 3개월 예약을 표시. 해당 기간의 예약은 건수 제한으로 누락하지 않는다. 첫 화면은 요약 필드만 요청하고 상세 메모·원본 셀·수식·색 구간은 포함하지 않음. |
| 목록 이동 | 3개월 데이터를 월별 또는 페이지별로 나누어 전송하더라도 화면에서는 같은 3개월을 모두 보여주고 추가 로딩 상태를 표시. 월 이동 시 3개월 창을 한 달씩 옮김. 검색은 입력을 잠시 멈춘 뒤 서버에서 수행. |
| 예약 상세 | 선택한 예약의 일정, 결제, 메모만 요청. 원본 그리드와 긴 명단은 해당 탭을 열 때 로딩. |
| 데이터 전송 | 중복 조인을 줄인 목록 전용 조회, 필요한 열만 선택, 날짜·시장·코드 검색 인덱스. 파일 전체를 브라우저로 내려받지 않음. |

기존 05의 예약 목록 요청은 1~6일차, 메모, 결제 필드까지 한 번에 가져오고 페이지 크기 제한이 명시되지 않았다. 이를 요약 조회와 상세 조회로 나누는 것이 첫 성능 작업이다. 기존 02/05의 24시간 IndexedDB 캐시는 개인정보 노출과 오래된 값 표시를 함께 검토해 범위를 축소한다. 전면 오프라인 수정은 첫 범위에 넣지 않는다.

초기 성능 목표는 필리핀 현지의 느린 연결을 흉내 낸 시험 환경(다운로드 약 1.6 Mbps, 왕복 지연 300 ms)에서 3개월 창의 첫 화면 요약이 3초 내 보이고, 나머지 예약도 누락 없이 점진적으로 표시되며, 상세 탭은 요청 후 3초 내 핵심 정보를 보이는 것이다. 이 수치는 구현 후 실제 기기/회선에서 측정하고 조정한다. 수치보다 중요한 실패 기준은 빈 화면에서 장시간 기다리는 일, 3개월 중 일부 예약이 페이지 제한 때문에 사라지는 일, 한 번의 요청으로 모든 시트를 받는 일, 저장 실패를 성공처럼 보이는 일이다.

## 8. 구현 순서와 완료 기준

### 단계 1: 설계·이관 준비

새 Supabase 프로젝트를 만들고 현재 운영 DB는 이전 대상으로 보지 않는다. 프로젝트의 실제 DB 설정을 구현 시작 시 확인한다. 엑셀 두 파일의 가져오기 미리보기, 원본 보존 구조, 중복/모호성 검토 기준을 확정한다. 사용자 제공 코드·색·정산 규칙은 그때 반영한다.

### 단계 2: 최소 운영 화면

즉시 접속과 관리자 권한 모달, 필리핀·태국·일본 예약 공간, 각 공간의 빠른 예약 목록·상세, 원본 보기, 필리핀 시제, 클락 거래처별 협력업체 바우처 폴더, 일본 수배 항목, 취소·변경 이력을 연결한다. 태국에는 별도 예약 공간을 두되 원본·규칙이 없으므로 임의 데이터나 자동 계산은 넣지 않는다. 같은 UI 구성요소를 데스크톱과 모바일에서 사용한다.

### 단계 3: 저장·검증

예약과 일정, 확인번호, 결제·비용의 추가·수정을 지원한다. 신규 예약 코드는 현행 시스템 형식으로 추천하거나 수기 입력한다. 저장 전후 값, 원본 출처, 변경 이력, 충돌을 확인한다. 예약 삭제는 관리자만 논리 삭제한다. 정산 자동 계산은 규칙 확정 후 추가한다.

### 단계 4: 기존 엑셀 이관

새 Supabase 연결과 일반 조회·추가·수정, 관리자 삭제, 코드 추천·수기 저장, 원본 보존 테이블의 권한 검증을 끝낸 다음 NEW 2026.xlsx와 일본 수배.xlsx를 이관한다. 파일·시트·행·셀·메모·색·수식 원문을 배치 단위로 적재하고 원본 코드와 신규 코드 추천값을 혼동하지 않는다. 이관 결과를 원본 셀 수·메모 수·행별 금액·중복 후보와 대조한 뒤 운영 화면에 공개한다.

### 인수 기준

- 두 엑셀의 10개 시트와 메모 3,436개를 좌표로 찾아볼 수 있다. 값 없는 메모, 숨김 행, 채우기 색과 조건부 서식도 원본 보기에서 확인된다.
- 같은 코드의 다른 손님/팀과 두 파일에 겹친 일본 예약이 임의 병합되거나 이중 매출로 집계되지 않는다.
- 클락의 다섯 거래처 탭을 바우처 폴더에서 각각 조회할 수 있다. 골프장·호텔 협력업체, 예약 연결, 확인번호와 지급 날짜/금액의 원문·메모·색을 확인할 수 있고, 복사 행을 중복 예약·중복 바우처로 집계하지 않는다.
- 필리핀·태국·일본 예약 공간에서 목록과 필터가 독립적으로 동작한다. 전체 검색 결과는 해당 국가 상세로 연결되고 다른 나라 규칙이 적용되지 않는다.
- 첫 진입은 필리핀 예약이며, 현재 달을 가운데로 이전·현재·다음 달의 예약이 모두 표시된다. 월 이동 시 3개월 범위가 한 달씩 이동하고 페이지 제한 때문에 예약이 누락되지 않는다.
- 비로그인 접속·일반 예약 조회·추가·수정이 가능하다. 삭제·이관·관리 설정 변경은 관리자 세션이 없으면 서버에서 거부되며 공개 가입 경로가 없다.
- 360px 모바일에서 국가 선택, 예약 검색, 일정·바우처 확인, 메모 수정과 저장 결과 확인이 가능하다. 일반 업무 화면에는 가로로 잘린 필수 버튼이 없다.
- 느린 연결에서 목록·상세의 단계별 로딩과 실패/재시도가 동작하며, 저장 실패가 성공으로 보이지 않는다.
- 코드·색·국가별 정산 규칙이 미확정인 데이터는 원본 그대로 보이고 자동 상태 변경이나 자동 계산의 근거로 사용되지 않는다.

## 10. 새 Supabase 프로젝트 사전 준비

새 DB를 처음부터 구축한다. 현 운영 DB를 복제하거나 기존 테이블을 그대로 가져오지 않고, 원본 엑셀과 확정된 업무 규칙을 기준으로 설계한다. 프로젝트 생성 직후에는 실제 손님 데이터를 넣지 않는다.

1. 개발용 새 프로젝트를 만들고 리전, 프로젝트 소유자, 관리자 접근을 정한다. 기존 웹앱 환경변수는 새 프로젝트 검증이 끝날 때까지 바꾸지 않는다.
2. 스키마를 재현 가능한 SQL 마이그레이션으로 관리한다. 첫 마이그레이션에는 국가·예약·원본 이관 배치/셀/메모/색·일정·확인번호·결제·변경 이력의 핵심 테이블과 관계를 둔다. 코드 뜻, 색상 뜻, 자동 계산 규칙은 아직 넣지 않는다.
3. 원본 보존 테이블과 운영 테이블을 분리하고, 배치 ID와 원본 좌표를 연결한다. 중복 코드가 있어도 모든 행을 적재할 수 있게 예약 코드에는 전역 UNIQUE를 걸지 않는다. 실패한 가져오기는 배치 단위로 검토·재시도한다.
4. 고정 관리자 계정 한 개를 만든 뒤 공개 가입은 끈다. 미로그인 일반 조회·예약 추가·수정과 관리자 전용 삭제·이관·설정 변경을 구분해 권한/RLS를 시험한다. 비밀키는 브라우저에 넣지 않는다.
5. 국가·날짜·코드 중심의 목록 인덱스와 가벼운 조회 뷰를 만든다. 필리핀·태국·일본 예약 화면은 동일 DB를 쓰되 국가 ID로 범위를 나눈다.
6. 새 Supabase 연결, 스키마, 권한, 목록·추가·수정·관리자 삭제와 신규 코드 추천/수기 입력의 동작을 먼저 검증한다. 그다음 실제 엑셀의 모든 셀·메모·색을 시험 배치로 이관해 누락·중복을 대조하고 운영 데이터로 전환한다. 이관 코드에는 신규 예약 추천 규칙을 적용하지 않는다.

Supabase는 [스키마 변경을 마이그레이션으로 관리](https://supabase.com/docs/guides/local-development/database-migrations), [가져오기 전 데이터 무결성과 성능을 준비](https://supabase.com/docs/guides/database/import-data), [공개 접근과 Auth 설정을 점검](https://supabase.com/docs/guides/security/production-checklist)하도록 안내한다. 지금은 이 순서만 확정하며, 프로젝트 생성·SQL 실행·환경변수 변경은 별도 구현 단계로 둔다.
